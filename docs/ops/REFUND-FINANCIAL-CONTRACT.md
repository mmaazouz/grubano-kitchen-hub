## 0 · Verdict of Phase 0 — the P0 is real, and it has TWO doors

**P0 — franchise royalty returned twice.** On a FRANCHISED order the application fee holds the franchisor's royalty (`royaltyChargedCents`, composed into `application_fee_amount` at `app/api/orders/[id]/pay/route.ts:272-276`, accrued as a `FranchiseRoyalty` `pending` row). A refund with `refund_application_fee:true` returns a prorated slice of that fee — royalty included — to the customer. The franchise settlement then pays `royaltyCents − refundedCents` (`lib/franchise-settlement.ts:83-84`). **Whoever refunds without bumping `FranchiseRoyalty.refundedCents` makes Grubano pay the royalty slice twice** (once to the customer, once to the franchisor).

Two doors leave `refundedCents` untouched today:

| Door | Path | Royalty-aware? | Evidence |
|---|---|---|---|
| **A — order route** | `POST /api/orders/[id]/refund` → `lib/refunds.ts refundPayment` | **NO** — never reads `FranchiseRoyalty`, never writes a `Refund` row | `app/api/orders/[id]/refund/route.ts:72-75`; `lib/refunds.ts` has 0 occurrences of royalty / prisma |
| **B — admin engine** | `POST /api/admin/refunds/run` → `lib/refund.ts executeRefund` | **YES** — split nests the royalty, `refundedCents` recomputed, settled royalty clawed back | `lib/refund.ts:294-365` |
| **W — external refund** | Stripe Dashboard refund → webhook `charge.refunded` | **NO** — ledger + loyalty + tip only | `app/api/webhooks/stripe/route.ts:623-756` (no `franchiseRoyalty` access) |
| tickets / deposits | `tickets/[id]/refund`, `reservations/[id]/refund-deposit` → rail A | n/a — **no Order row, no royalty possible** (`FranchiseRoyalty` keyed by `orderId`, channels pickup/delivery only) | `app/api/tickets/[id]/refund/route.ts:58`, `app/api/reservations/[id]/refund-deposit/route.ts:53` |

Doors A and B share the SAME `REFUNDS_ENABLED` flag (`app/api/orders/[id]/refund/route.ts:41`, `app/api/admin/refunds/run/route.ts:43`) → the instant the flag flips, door A is a double-payment on any franchised order. Door W is **ungated by design** (founder rule: the flag gates *initiation*, never reconciliation of an established Stripe refund — `LOYALTY-REFUND-CONTRACT.md §17`) → door W is reachable **today**.

The rejection note in both lib headers (« routing owner routes through the engine audited & REJECTED — tickets have no Order row, would take the live path dark ») is **obsolete for the ORDER route**: since P0-26 the order route is admin-only and gated by the same flag as the engine, and the ticket/deposit routes have no Order row so they are out of scope. No document with the « 10 divergences » exists in the repo (grep: 0 hits) — the divergences are re-derived in §4.

## 1 · Money decomposition on a routed order charge (facts)

`amount` (= `order.total`) = subtotal + deliveryFee + smallFee + tip − promo − loyaltyCredit.
`application_fee_amount` = `max(0, grossCommission − loyaltyCredit) + smallFee + tip + courierWithheld + royaltyCharged` (`pay/route.ts:272-276`); the restaurant's net = amount − fee. Stripe destination charge with `on_behalf_of` (`lib/stripe.ts:95-99`).

Inside the fee, Grubano is the **owner** of commission + smallFee only; it is the **custodian** of the tip (owed to the courier, `lib/courier-accrual.ts`), of courierWithheld (owed to the courier) and of royaltyCharged (owed to the franchisor, `FranchiseRoyalty`).

## 2 · Refund split — `computeRefundSplit` (facts, `tests/refund-split.test.ts` 10/10)

`T` charge total, `F` fee (clamped ≤ T), `R` royalty (clamped ≤ F), `Cprev` already refunded (live Stripe), `C = Cprev + amount`.
`feeCum(x) = round(F·x/T)`, `royCum(x) = round(feeCum(x)·R/F)`; per-refund deltas telescope → `restaurantReverse + applicationFeeRefund === amount` exactly; N partials sum exactly to F, T−F, R (`lib/refund.ts:116-153`). Both refund libs pass `refund_application_fee:true, reverse_transfer:true` only when `pi.transfer_data` is set (`lib/refund.ts:245`, `lib/refunds.ts:73`) — Stripe prorates the fee itself; our split is the *prediction* of Stripe's proration.

⚠️ **Prediction vs Stripe truth in the ledger.** The eager ledger line written by `finalizeRefund` uses OUR predicted `applicationFeeRefundCents` (`lib/refund.ts:329-341`), while the webhook backstop uses **Stripe's REAL fee refund** (`webhook:651-672`); both are keyed on the same `re_…`, whichever lands first wins → a rounding divergence between prediction and Stripe would be frozen in the ledger. Stripe's rounding rule: see §9.

## 5 · Door W — external (Dashboard) refund reconciliation (decision D-B)

`charge.refunded` is already the single reconciliation point for the ledger (`webhook:672-698`) and for loyalty (`:709-729`). Phase 2 adds **royalty accounting** there, with the same properties: derived from the Stripe truth — **the cumulative sum of the `succeeded` refunds** of the charge (the list the handler already filters at `webhook:646`; **never `charge.amount_refunded`**, which counts a still-`pending` refund that may later fail — critic #2) — cumulative-target (`royCum(Σ succeeded)` = `computeRefundSplit({alreadyRefunded:0, amount: Σ succeeded}).cumulativeRoyaltyRefundedCents`), **monotone**, **cross-rail** (`max(Σ Refund rows, royCum(Σ succeeded)) + Σ dispute slices`, capped at `royaltyCents`). Telescoping identity (verified by the critic, #9): Σ engine slices == royCum(cumul) for the same (T,F,R), and engine and webhook read the same `charge.amount`, `charge.application_fee_amount`, `FranchiseRoyalty.royaltyCents` → an engine refund and an external refund of the same money reconcile to the **same** target — no double count, no under count. Idempotent by construction (a target, not a delta). Cross-rail tolerance: dispute slices are computed from a different `alreadyRefunded` origin → `royCum(X)+royCum(D)` may differ from `royCum(X+D)` by **±1 cent**; the cap absorbs the high side, the low side is a documented 1-cent tolerance (dispute-then-refund is mostly academic — Stripe normally refuses a refund on a disputed charge, `charge_disputed`, UNVERIFIED).

**No money movement from the webhook.** A `settled`/`settling` royalty hit by an **EXTERNAL** refund — identified as a Stripe Refund **without** `metadata.grubano_refund_row` (the engine tags every refund it creates, `lib/refund.ts:246`) — is **flagged** (`MONEY REVIEW` log + best-effort admin alert with the exact slice), never auto-reversed: the founder principle « no unattended external financial effect » (`lib/refund.ts:71-80`) applies to a clawback that no Grubano human initiated. Engine-originated refunds are not flagged (the engine's own step (a) claws back). Founder-visible residual: that external clawback is a human action (admin rail after Phase 3, or a Stripe Dashboard transfer reversal).

**Webhook as backstop for the engine (critic #11):** `finalizeRefund` steps (c) row `succeeded` and (d) `refundedCents` are not atomic; if (d) throws, the D-B target heals `refundedCents` on the next `charge.refunded`/`refund.updated` delivery (same value by the identity). Recorded, not wrapped.

## 6 · Stripe processing fee & courier tip on partial refunds (decisions D-D, D-E)

- **Stripe processing fee** (`stripeFeeAmount` on the payment line = real balance-transaction fee, `webhook:556-565`; `0` on refund lines, « zero movement, affirmed », `lib/ledger.ts:50-51`). Stripe does not return its processing fee on a refund (see §9). Model: Grubano's **exposure** on any refund includes the processing fee already paid (unchanged) — nothing moves, nothing to book. Decision: **keep `stripeFeeAmount = 0` on refund lines** (movement truth) and make the retained fee explicit in the pure exposure model + tests (no ledger change).
- **Courier tip.** The fee refund returns `tip·ΔC/T` to the customer (the tip is inside F), while `clawbackCourierTip` fires only on a TOTAL refund (`webhook:732-750`, `lib/courier-accrual.ts:208-227`). Decision (default; founder may override): **partial refund → the courier keeps the whole tip (service performed — mirrors « the COURSE stays acquired »), Grubano absorbs the returned tip slice**; full refund → existing clawback of unpaid tips (paid tips kept, logged). The absorbed slice is **computed explicitly** (`computeRefundExposure`) and tested, never silent.

## 7 · Tripartite conservation identity (decision D-C — new test)

For every refund event, and cumulatively, with `a` = amount refunded to the customer:
`customerΔ = +a` · `restaurantΔ = −restaurantReverse` · `franchisorΔ = −royaltySlice` (via `refundedCents` or clawback) · `courierΔ = −tipSlice` only when clawed (full refund, unpaid tip), else 0 · `grubanoΔ = −(applicationFeeRefund − royaltySlice − courierΔabs)` · `stripeΔ = 0`.
**Identity:** `customerΔ + restaurantΔ + grubanoΔ + franchisorΔ + courierΔ + stripeΔ = 0` at every step, integer cents, zero residue. After a FULL refund: customer +T, restaurant −(T−F), franchisor −R, courier −tip (if clawed) else 0, Grubano the rest, Stripe keeps its fee. Proven on STANDARD (R=0) and FRANCHISE (R>0) × full / partial / multiple partials with odd cents.

## 8 · Failed / pending refund truthfulness (decision D-F)

- `finalizeRefund` marks `succeeded` + eager ledger + returns `ok:true` **only when `stripeRefund.status === 'succeeded'`**. A `pending` Stripe refund → the row stays `pending` **with `stripeRefundId` recorded**, and the outcome is a **distinct non-ok variant** `{ok:false, status:202, pending:true, refundId, stripeRefundId, amountCents, error:'Remboursement en attente côté Stripe.'}` (critic #4: every existing caller tests `result.ok` as « money moved » — `lib/claims.ts:246`, `webhook:446` — so pending must never be `ok:true`). Routes answer **202 `{status:'pending', …}`** and send **no** email; claims keep the claim `refunding` with the `refundId` (no `refundError`); the ghost-order branch falls to `reconcile_manual` (conservative, documented). A later `executeRefund` call (RESUME-FIRST) or the `refund.updated` webhook finalizes once succeeded. **RESUME-FIRST + pending = an order-level lock** (any new partial on that order answers `pending`, up to Stripe's 30-day window) — accepted, documented; a resumed row ignores the caller's `amountCents` and says so (`resumed:true`, explicit message — critic #17).
- **Eager ledger = Stripe truth, not prediction (§2 ⚠️ closed):** `finalizeRefund` re-lists the charge's **succeeded** refunds and the fee's refunds (the fresh-path `charge` object is PRE-refund — critic #8) and resolves the real fee refund with ONE pure helper shared with the webhook: chronological index-matching **accepted only when counts match AND every `|feeRefund_i − round(F·amount_i/T)| ≤ 1`** (second-granular `created` makes same-second ties ambiguous); otherwise the eager line is **skipped** (the webhook backstop writes it, prorata fallback + `MONEY REVIEW`). The `Refund` row keeps the predicted split for audit; prediction ≠ truth is logged `MONEY REVIEW` (rounding evidence for the founder). The ledger never freezes a predicted cent.
- New webhook branch **`refund.updated` / `refund.failed`** (object = Stripe Refund, the status oracle per §9.4; `charge.refund.updated` is deprecated). Row matching order: `metadata.grubano_refund_row` first, `stripeRefundId` second (a lost create response leaves `stripeRefundId` null — critic #12). `succeeded` → finalize the matching `pending` row (idempotent, same `finalizeRefund`); `failed` / `canceled` → row `status='failed'`, `idempotencyKey` suffixed `:failed:<re_id>` (the cumul cursor is released), no ledger line (none was written), loyalty untouched (it reconciles succeeded refunds only), `MONEY REVIEW` log + admin alert. **These two events are NOT subscribed on the Stripe TEST endpoint today** (read-only probe: `we_…7ueK` = `payment_intent.amount_capturable_updated, payment_intent.canceled, payment_intent.succeeded, charge.refunded`; `we_…tpvK` = `account.updated`) → **founder readiness action** (§13). Until then the oracle is RESUME-FIRST on the next engine call — truthful (never « effectué »), just slower.
- **Fail-closed after a failure (§9.5):** because Stripe does not restore the reversed transfer on a failed refund, `executeRefund` **refuses** (409 « reprise manuelle requise ») any new refund on an order that carries a `failed` row with a `stripeRefundId` — a blind retry with `reverse_transfer:true` would debit the restaurant twice. **The lock is permanent and explicit** (critic #13): the human path is the Stripe Dashboard (re-transfer the reversed net to the restaurant, then refund without `reverse_transfer`), and the order stays visible in the failed-refund alert. No automation, no unblock route in Phase 2.
- Email wording unchanged (« effectué ») because it is now sent only after Stripe `succeeded`.

## 9 · STRIPE SEMANTICS FACT SHEET (agent A — docs.stripe.com fetched 2026-09-03; FACT = documented, UNVERIFIED = not stated in docs)

1. **Fee refund proration — FACT.** `refund_application_fee:true` refunds the whole fee on a full refund, else « an amount proportional to the amount of the charge refunded » (api/refunds/create; worked example 100/5/40 → 2). **Rounding rule — UNVERIFIED** (no doc states floor/half-up) → never trust a recomputation for the ledger; read the real `fee_refund.amount` (item 8).
2. **Where the money moves — FACT.** On a destination charge with `application_fee_amount`, the transfer to the connected account is the FULL charge amount and the fee is pulled back to the platform. `reverse_transfer:true` reverses **proportionally = the gross refund amount X** from the connected account; the fee refund then **credits the connected account** (« refunded to the Stripe account from which the fee was originally collected »); the customer is paid from the PLATFORM balance. Net: connected account −(X − feeRefund), platform −feeRefund → **our split's net assumption is CONFIRMED** (two balance transactions, not one netted debit). Refunding the fee on a destination charge **requires** reversing the transfer (connect/destination-charges#issue-refunds).
3. **Stripe processing fee — FACT.** Never returned on a refund (« processing fees from the original transaction aren't returned »). On destination charges the **PLATFORM bears Stripe fees, with or without `on_behalf_of`** (`on_behalf_of` only selects the fee schedule's country). → D-D confirmed: zero movement, Grubano's sunk cost.
4. **Refund status lifecycle — FACT.** `status ∈ {pending, requires_action, succeeded, failed, canceled}`; a card refund can be `pending` at creation (insufficient platform balance, unsettled charge) and later `failed` (bank failure up to 30 days; `insufficient_funds` after the pending window); `failure_balance_transaction` re-credits the platform. **Events — FACT:** `refund.created`, `refund.updated`, `refund.failed`, `charge.refunded` (« whenever a charge is refunded, including partial », emitted at refund **creation** → it CAN carry a still-`pending` refund), `application_fee.refunded`, `transfer.reversed`. `charge.refund.updated` is deprecated/limited. → the status oracle is **`refund.updated` / `refund.failed`** (object = Refund, carries `payment_intent`, `charge`, `metadata`, `status`, `failure_reason`). Whether `charge.amount_refunded` is decremented on failure — **UNVERIFIED** → never rely on it.
5. **Failed refund on a destination charge — FACT.** Funds return to the PLATFORM balance; **the reversed transfer is NOT auto-restored** (« Create a Transfer to move the funds to the connected account, as needed »). → after a failure the restaurant has been debited X and credited feeRefund while the customer got nothing; a blind retry with `reverse_transfer:true` would **debit the restaurant a second time**. Phase 2 policy: **fail-closed** (§8).
6. **External Dashboard refund — FACT** that it is possible; **UNVERIFIED** whether the Dashboard defaults to reversing the transfer / refunding the fee on a destination charge. → the webhook must never assume: detect via `refund.transfer_reversal` (nullable) and the real fee refunds list.
7. **`transfers.createReversal` — FACT.** Partial reversals allowed until fully reversed; requires the connected account's available balance ≥ amount (else `balance_insufficient`, no negative balance); refund+reverse_transfer with insufficient connected balance → the refund request itself **errors** (no pending refund created).
8. **Idempotency keys — FACT.** Pruned after ≥ 24 h; same key + different params = error.
9. **Real fee refund — FACT.** `GET /v1/application_fees/{fee}/refunds` → `fee_refund.amount` (integer); stripe-node `applicationFees.listRefunds(feeId)` (already used at `webhook:657`). The Refund object has no pointer to its fee refund → correlate by charge + chronological index (the webhook's existing rule).
